# Nivis Registry — Architecture & Design

## The thesis

Every OpenTofu/Terraform provider is **Nivis-compatible by design**: Nivis drives unmodified provider
binaries over the plugin protocol (`GetProviderSchema` → `PlanResourceChange`/`ApplyResourceChange`).
So the registry does not need to "port" providers. Its job is to make them **discoverable** and to
publish **Nix-native documentation** for each — documentation derived from the provider's own schema,
not from hand-written HCL prose.

## Why schema-derived docs (and why it's legally clean)

`nivis gen` already calls `GetProviderSchema` on a provider binary and emits typed **Nix constructors**:
every flat argument, every nested block with the correct list/single/set/map shape, plus computed
outputs — each documented inline. That output **is** the per-provider reference, in Nivis terms.

- **Schema is the provider's own API surface**, obtained from the binary we are licensed to run — not
  scraped prose. There is no documentation-dataset licensing question for the reference body.
- OpenTofu, by contrast, **scrapes markdown from each provider's GitHub repo** and runs a license
  allowlist because the legal standing of that dataset is unclear. We sidestep that for the core product.
- The reference always **matches the actual binary**, because it comes from the binary.

(Optional later enrichment — prose/examples from upstream repos, license-gated, with an HCL→Nix
transpiler — is roadmap, not v1. See milestone `06`.)

## Architecture (OpenTofu's split, adopted in full)

```
                 ┌──────────────────────────────────────────────────────────┐
                 │  BACKEND GENERATOR (Go, this repo, tools/)                 │
 seed.json  ───▶ │  seed → extract (verify+nivis gen) → compat → generate     │ ───▶ static JSON contract
                 │                                                            │      + Nix-constructor docs
                 └──────────────────────────────────────────────────────────┘
                                                                                       │
                 ┌──────────────────────────────────────────────────────────┐         │ reads (HTTP/files)
                 │  FRONTEND (forked opentofu/registry-ui, React+Vite SPA)    │ ◀───────┘
                 │  routing/search kept; resource-page rendering ADAPTED to   │
                 │  show Nix constructors + compat badge                      │
                 └──────────────────────────────────────────────────────────┘
```

**Key property:** the SPA is **data-agnostic** — it consumes a JSON contract, not OpenTofu concepts.
The same contract is served by static files now (S3/CloudFront) and by a dynamic API later
(API Gateway + Lambda). The frontend is **built once, never thrown away**. The only Nivis-specific code
is the **backend generator**, which we would write under any option.

## The JSON contract

Mirror registry-ui's contract (`backend/internal/server/openapi.yml` in `opentofu/registry-ui`):

```
registry/docs/providers/{namespace}/{name}/{version}/index.json   # lists resources/datasources/functions + compat badge
registry/docs/providers/{namespace}/{name}/{version}/<item>...     # per-item document (Nix-rendered body)
```

The difference from OpenTofu: the per-item document body is the **rendered `nivis gen` constructor**
(signature + types + computed outputs), not scraped HCL. The provider `index.json` additionally carries
the **compat record**.

## Compatibility tiers & badge (four independent axes)

Be honest; never conflate "should work" with "proven":

1. **Schema-extractable** — did the pipeline download the binary and get its schema? (machine-verified)
2. **Protocol** — 5.0 / 6.0, from upstream metadata. (Nivis handles both; 6.0 untested today.)
3. **Architectures** — **Nivis-supported ∩ published `targets`** (a provider that ships only
   linux/amd64+darwin can't serve linux/arm64 users regardless of Nivis).
4. **E2E tier** — `none` | `verified`, from a small hand-maintained allowlist (only a couple verified today).

The default badge is **"compatible by design"** (axes 1–3). **"E2E verified"** is the small, growing,
linkable subset. A provider with no allowlist entry is never shown as `verified`.

## Hosting

- **v1**: static contract + SPA on **S3 + CloudFront** (we are AWS partners).
- **Later**: **API Gateway + Lambda** serving the same contract + a search endpoint (additive; the SPA
  does not change). This is milestone `06`.

## Repo layout

```
AUTONOMOUS-BUILD.md     # the master brief for the autonomous run
REGISTRY-DESIGN.md      # this file
flake.nix               # plain-nix (no flake-utils), 4 systems, nivis input, devShell
nix/                    # nix helpers
seed.json               # pinned seed manifest (generated by tools/seed)
tools/
  seed/                 # derive+pin seed from the popularity API
  extract/              # resolve+verify binary → nivis gen → schema + .nix
  compat/               # compute compat tier/badge
  generate/             # emit the registry-ui JSON contract from extraction output
frontend/               # forked registry-ui SPA (rendering adapted to Nix)
registry/docs/...        # generated static contract (build output)
.beans/                 # milestones + epics
openspec/               # change proposals + specs + tasks
```

## Upstream relationship (downstream overlay)

v1 **vendors a snapshot** of the needed OpenTofu provider metadata. The registry is a *downstream
overlay*: upstream stays the source of truth for "what exists + where the binaries are"; our value is
the overlay (compat + Nix docs). A release-feed (RSS) **delta sync** that replaces the snapshot is
milestone `06`, not v1.
